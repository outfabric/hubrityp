## Why

Após o `auth-account-creation` entregar o caminho de onboarding, o sistema ainda não satisfaz os requisitos do PRD 01 que protegem o login (RF-01.06–08, RNF-01.05) nem oferece os caminhos alternativos de autenticação (RF-01.10–12) e recuperação de senha (RF-01.13–15) que o usuário psicólogo espera. Sem lockout, o login fica vulnerável a brute force; sem reset de senha, qualquer esquecimento força contato com suporte; sem Google OAuth, perdemos uma redução grande de fricção no onboarding ("não quero lembrar de mais uma senha"). Este change fecha essas lacunas e completa a base regulatória de logs de autenticação (RNF-01.05) que o sistema precisa antes de tocar dados clínicos.

## What Changes

- **Lockout por tentativas de login** — RF-01.08: 5 falhas em 15 min bloqueiam a conta por 30 min, com email ao usuário a cada bloqueio; após 3 bloqueios consecutivos, a conta exige reset de senha antes de poder voltar a logar (estado `requires_password_reset` em `profiles`).
- **Anti-enumeração no login** — RF-01.06: mensagem de erro genérica ("E-mail ou senha incorretos") sempre que o login falha, sem revelar se a conta existe; o contador de tentativas só incrementa para emails válidos no backend.
- **"Manter conectado"** — RF-01.06 + RNF-01.21: checkbox no `LoginForm` controla a duração da sessão. Marcado → 24h; desmarcado → cookie de sessão (some ao fechar o browser).
- **Recuperação de senha** — RF-01.13–15: rota `/forgot-password` com mensagem genérica anti-enumeração; rota `/reset-password` aplica a policy strong-password do signup; após reset, **todas** as sessões ativas do usuário são invalidadas e um email de aviso é enviado.
- **Google OAuth** — RF-01.10–12: provider Google habilitado no Supabase; primeiro acesso via Google sem `profile` dispara fluxo `/onboarding/complete-profile` que coleta CRP/UF + 3 aceites antes de criar a `profiles` row; conta Google cujo email já existe como conta tradicional dispara fluxo de account linking exigindo confirmação da senha tradicional.
- **Logout com revogação server-side** — RF-01.22: `signOut` passa a invalidar o refresh token no backend (via `supabase.auth.admin.signOut(jwt)` no service role) e marca `auth_sessions.revokedAt`; logout afeta todas as abas do mesmo refresh token.
- **Auth logs completos** — RNF-01.05: novos eventos persistidos com `ip` + `user_agent`: `login_success`, `login_failure`, `lockout_started`, `lockout_consecutive_threshold_reached`, `password_reset_requested`, `password_reset_completed`, `social_linked`, `oauth_signup`, `logout`. Job de housekeeping deleta logs >6 meses.
- **Conta `suspended`/`cancelled`** — copy específica de erro no login + log do attempt; sem revelar diferença entre "não existe", "suspensa" e "cancelada" do lado do client.
- **Coluna `lockout_until` e `failed_login_count`** — adicionadas a `profiles` para o lockout; alternativa a uma tabela separada de `login_attempts` (ver design).
- **Tabela `oauth_identities`** — para account linking explícito (provider + provider_user_id) e diferenciação entre conta criada via OAuth e conta tradicional posteriormente vinculada.
- **BREAKING (interno)**: `signIn` Server Action passa a retornar `{ ok: false, error: 'locked_out' | 'requires_password_reset' | 'account_unavailable' | 'invalid_credentials' | 'unknown' }` em vez do conjunto reduzido atual; `LoginForm` precisa renderizar copy para cada caso.
- **Cobertura de testes**: unit (validators de reset, lockout state machine), integration (Server Actions de reset, lockout sob concorrência, Google OAuth callback, logout server-side, RLS para `oauth_identities`), e2e seeded (forgot/reset flow, lockout após 5 tentativas, "manter conectado" muda duração de cookie, logout em uma aba derruba a outra), e2e real (smoke do Google OAuth pode ficar como out-of-scope se exigir credenciais externas — confirmar em design).

## Capabilities

### New Capabilities

- `password-recovery`: Fluxo de recuperação de senha — `/forgot-password` (mensagem genérica anti-enumeração + envio de link 1h), `/reset-password` (aplica strong password policy, invalida todas as sessões ativas, email de aviso ao usuário), Server Actions `requestPasswordReset` e `resetPassword`, política de invalidação de sessões via `supabase.auth.admin.signOut` por user_id.
- `oauth-google`: Login social com Google — provider habilitado, callback `/auth/callback` (compartilhado com email verification mas com branch oauth-aware), tela `/onboarding/complete-profile` para coletar CRP/UF/aceites em primeiro acesso, fluxo de account linking quando email Google bate com conta tradicional, tabela `oauth_identities`.

### Modified Capabilities

- `authentication`: `signIn` ganha lockout (5/15min → 30min), suporte a "manter conectado" (cookie session vs 24h), exige `requires_password_reset` post-3-bloqueios, mensagem genérica anti-enumeração e codificação de erro mais granular. `signOut` passa a revogar refresh token via service-role + atualiza `auth_sessions.revokedAt`. Middleware reconhece o estado `requires_password_reset` e redireciona para `/forgot-password`. `LoginForm` ganha checkbox "Manter conectado" e copy para os novos erros.
- `data-layer`: Adiciona à tabela `profiles` as colunas `failed_login_count INT NOT NULL DEFAULT 0`, `lockout_until TIMESTAMPTZ`, `consecutive_lockouts INT NOT NULL DEFAULT 0`, `requires_password_reset BOOLEAN NOT NULL DEFAULT false`. Adiciona tabela `oauth_identities` (`user_id`, `provider`, `provider_user_id`, `linked_at`, `UNIQUE(provider, provider_user_id)`) com RLS (`select_own`). Estende set de eventos válidos em `auth_logs` (sem schema change — coluna já é TEXT) e adiciona job/cron de retenção de 6 meses para `auth_logs`. Index novo em `profiles(failed_login_count, lockout_until)` para queries de lockout.

- **Código novo**: `src/modules/auth/server/lockout.ts` (state machine + helpers), `src/modules/password-recovery/` (módulo novo: forgot/reset Server Actions, validators, components), `src/modules/oauth/` (módulo novo: provider helpers, complete-profile flow, account linking), `src/app/(auth)/forgot-password/` + `actions.ts`, `src/app/(auth)/reset-password/[token]/`, `src/app/(app)/onboarding/complete-profile/`, `src/shared/db/schema/auth/oauth-identities.ts`, novas migrations Drizzle (`0002_login_hardening.sql`, `0003_oauth_identities.sql`), novos primitives shadcn se necessário (`switch` para "manter conectado" — alternativa: usar `checkbox` existente).
- **Código modificado**: `src/middleware.ts` (case para `requires_password_reset`, gating de `/onboarding/complete-profile`), `src/modules/auth/server/login.ts` (lockout, "manter conectado", erros granulares), `src/modules/auth/server/logout.ts` (revogação server-side), `src/modules/auth/components/login-form.tsx` (checkbox "Manter conectado", copy nova), `src/modules/auth/lib/login-input-schema.ts` (campo `keepLoggedIn: z.boolean()`), `src/app/(app)/actions.ts` (delegação atualizada), `src/modules/registration/index.ts` (nada — registro não muda), `docs/design-system/testid.md` (Wave-5 IDs).
- **Dependências externas**: Resend (ou Supabase SMTP local) para emails de aviso pós-reset (RF-01.15) — em dev usa o inbucket. - **Banco de dados**: ALTER TABLE em `profiles` (4 colunas), CREATE TABLE `oauth_identities`, novo índice em `profiles`, novo cron Inngest (ou similar) para purge de `auth_logs` (job pode ficar como TODO se Inngest ainda não estiver wired — declarar no design).
