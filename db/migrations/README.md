# Migrations

Generated by `drizzle-kit` from the schema in `db/schema/**/tables.ts`.

## Workflow

```bash
npm run db:generate     # writes a new SQL file describing the schema diff
# → manually append RLS policy SQL (see template below)
npm run db:migrate      # applies pending migrations against $DATABASE_URL
```

## Why RLS SQL is appended manually

Drizzle does not generate `ENABLE ROW LEVEL SECURITY` or `CREATE POLICY`
statements. Every table introduced under `db/schema/<domain>/tables.ts` must
have its policies declared in `db/schema/<domain>/policies.ts` and **appended
manually** to the generated migration file before commit.

The integration suite enforces this contract — the policy-coverage test
(`__tests__/integration/policy-coverage.int.test.ts`) fails the build if any
table referenced from `db/schema/**/tables.ts` lacks a matching
`CREATE POLICY ... ON <table>` line in `db/migrations/**`.

## Canonical owner-scoped template

For any table tied to a single owner via `owner_id uuid REFERENCES auth.users`:

```sql
ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;

CREATE POLICY "owner can select" ON <table>
  FOR SELECT TO authenticated
  USING (auth.uid() = owner_id);

CREATE POLICY "owner can insert" ON <table>
  FOR INSERT TO authenticated
  WITH CHECK (auth.uid() = owner_id);

CREATE POLICY "owner can update" ON <table>
  FOR UPDATE TO authenticated
  USING (auth.uid() = owner_id)
  WITH CHECK (auth.uid() = owner_id);

CREATE POLICY "owner can delete" ON <table>
  FOR DELETE TO authenticated
  USING (auth.uid() = owner_id);
```

Multi-tenant variants (e.g., `psychologist → patients → records`) extend the
USING/WITH CHECK clauses with the ancestor-ownership join, but every
owner-scoped policy keeps this base shape so a reviewer can verify
correctness in seconds.

## Rollback

There is no automatic rollback. To revert a migration locally, drop the
affected schema and re-run `npm run db:migrate`, or `npm run supabase:reset`.
In production, write a forward-only fix migration.
